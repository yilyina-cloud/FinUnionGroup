# Ключевые сущности

## Состав модели

Сохранены десять стартовых сущностей: клиент, счёт, карта, кредит, договор, транзакция, платёж, продукт, обращение клиента и справочник.

Добавлены:

- Тариф — для согласования различающихся ставок, комиссий и условий обслуживания.
- Документ — для хранения метаданных и связей договорных документов, материалов обращений и архивных файлов.

Под справочником понимается запись классификатора: валюта, статус, тип операции, отделение или сегмент. Продукт и тариф выделены отдельно, поскольку имеют собственные связи и жизненный цикл.

FU — FinUnion, RB — RetailBank.

Реквизиты внешнего получателя платежа не требуют создания клиента в CRM. Ссылки на внутреннего клиента или счёт добавляются, если сторона обслуживается в группе.

Остаток счёта — состояние на определённый момент, получаемое из АБС. Он не редактируется независимо от учётных данных. Для аналитики могут храниться отдельные снимки остатков.

## Идентификация и сопоставление

Для интеграционных записей сохраняются:

- система-источник и локальный ID;
- версия или время изменения;
- время загрузки;
- ID загрузки или события.

Исходная запись определяется сочетанием «тип сущности + система + локальный ID». Одинаковые локальные номера в разных банках не означают один объект.

Правила сопоставления:

1. Клиенты сопоставляются по проверенным идентификационным данным с учётом типа лица. Одного совпадения ФИО или телефона недостаточно.
2. Единый customer_id связывается с локальными ID через CUSTOMER_ID_MAP. Слияния, разделения и изменения соответствий журналируются.
3. Неоднозначные совпадения передаются на ручную проверку без автоматического слияния.
4. Счета, договоры, карты и кредиты сохраняют собственную идентичность. Один клиент не означает один договор или счёт.
5. Карточная авторизация не считается учётным движением. Для отчётности по проводкам используется запись Core, а сведения Cards дополняют её.
6. Тарифы и справочники сопоставляются по смыслу, а не только по коду. Условия действующих договоров не меняются автоматически.

## Подтверждение качества

Перед настройкой правил проводится профилирование источников: пропуски, дубли, форматы, статусы и фактические связи. Перечисленные проверки являются проектными предложениями, а не результатами обследования.

| Проверка | Точка контроля | Действие при нарушении |
| --- | --- | --- |
| Формат, обязательные поля, версия сообщения | Граница приёма | Изолировать запись с причиной и сохранить возможность повторной обработки |
| Однозначность сопоставления клиентов | Customer Hub | Передать спорный случай Data Steward |
| Ссылки на клиента, договор и справочники | Подготовка согласованного набора | Проверить порядок поступления данных; повторить обработку после получения зависимости |
| Полнота и согласованность финансовых данных | Перед публикацией витрины | Блокировать публикацию затронутого набора при необъяснённых расхождениях |

Сверки выполняются для одинакового состава данных на один момент времени с учётом валют, статусов и даты проводки. Совпадение общей суммы не заменяет проверку состава записей и связей.

Владелец данных утверждает правила и пороги. Data Steward разбирает дефекты. Инженер реализует проверки и обеспечивает их выполнение. Для карантина до запуска назначаются ответственный, срок разбора и порядок повторной обработки.
