# Логическая модель данных

Модель описывает ключевые связи для интеграции FinUnion и RetailBank. Она не предполагает перенос всех сущностей в одну физическую БД.

ERD разделена на три представления. Повторяющиеся сущности обозначают одни и те же объекты:

- [Клиенты, продукты и договоры](diagrams/contracts.mmd)
- [Платежи, карты и движения](diagrams/operations.mmd)
- [Обращения и документы](diagrams/servicing.mmd)

PK и FK обозначают логические ключи и ссылки. Межсистемные ссылки проверяются при интеграции, даже если физический внешний ключ между БД невозможен.

## Связи и кардинальности

| Связь | Кардинальность и правило |
| --- | --- |
| Клиент — договор | M:N через AGREEMENT_PARTY. У договора один или несколько участников с ролями; у клиента может не быть договоров |
| Продукт — договор | Каждый договор относится к одному продукту; продукт может не иметь договоров |
| Продукт — тариф | Тариф относится к одному продукту; у продукта может быть несколько версий тарифов |
| Тариф — договор | Договор использует не более одной базовой версии тарифа в текущем представлении. Индивидуальные условия и история сохраняются отдельно |
| Договор — счёт | Счёт имеет один основной договор обслуживания; договор может включать несколько счетов |
| Договор — кредит | Кредит относится к одному договору. В рамках модели один договор содержит не более одного кредита |
| Счёт — карта | Карта связана с одним основным счётом; у счёта может быть несколько карт |
| Клиент — карта | У карты один держатель, который может отличаться от владельца счёта |
| Договор — карта | У карты один договор выпуска/обслуживания; он может отличаться от договора счёта |
| Счёт — транзакция | Каждая транзакция относится к одному счёту. Внутренний перевод создаёт отдельные движения по счетам |
| Платёж — транзакция | У платежа от нуля до нескольких транзакций. У транзакции может не быть платежа, например при начислении процентов |
| Карта — транзакция | Транзакция может относиться к одной карте; не все движения являются карточными |
| Транзакция — сторно | Корректирующая запись может ссылаться на одну исходную транзакцию; у исходной записи может быть несколько корректировок |
| Клиент — обращение | Обращение относится к одному идентифицированному клиенту |
| Договор — обращение | Ссылка на договор необязательна |
| Документ — клиент/договор/обращение | Каждая ссылка необязательна, но хотя бы одна должна быть заполнена |
| Справочник — сущности | Значение проверяется по типу справочника и периоду действия |

## Дополнительные структуры

### CUSTOMER_ID_MAP

Хранит соответствие:

«система-источник + локальный ID клиента → единый customer_id».

В текущем состоянии локальная запись связана не более чем с одним единым клиентом. Несколько записей одной CRM могут ссылаться на одного клиента, если в источнике обнаружены дубли.

Диаграмма показывает текущее соответствие. История хранится отдельно с периодом действия, причиной и автором изменения.

### AGREEMENT_PARTY

Связывает клиента с договором и хранит роль и период участия. Позволяет представить владельца, заёмщика, созаёмщика и других участников.

CUSTOMER_ID_MAP и AGREEMENT_PARTY — вспомогательные структуры, а не дополнительные бизнес-сущности из основного списка.

### REFERENCE_VALUE

Представляет версию значения классификатора. На диаграммах показаны только отдельные справочные связи, чтобы сохранить читаемость.

У валют, статусов, категорий и типов документов разные допустимые наборы значений. Универсальная структура справочника не означает общий список кодов для всех полей.

## Ограничения целостности

- Денежные суммы хранятся в точном десятичном формате вместе с валютой.
- Суммы разных валют не складываются без явно заданного пересчёта.
- Повторная доставка одной версии исходной записи не создаёт новый объект.
- Ссылки на клиента разрешаются через CUSTOMER_ID_MAP.
- Неразрешённые ссылки сохраняются для разбора и повторной обработки.
- Тариф договора должен относиться к тому же продукту.
- Исторические тарифы и справочники интерпретируются на соответствующую дату.
- Сторно не уничтожает исходную финансовую запись.
- Объединение клиентов не удаляет их договоры, счета и историю операций.
- Проверки финансовой целостности учитывают правила исходной АБС. Эта модель не заменяет двойную запись и план счетов.

## Границы модели

Кардинальности являются проектными допущениями и проверяются при обследовании.

Если источники содержат мультивалютные карты с несколькими счетами, кредитные транши или документы с несколькими договорами, модель расширяется соответствующими связями до миграции.

Анонимные обращения в текущую модель не включены. Если они входят в объём миграции, связь обращения с клиентом становится необязательной.

Аналитическая модель Task3 отдельно определяет факты, измерения и детализацию строки, сохраняя бизнес-смысл сущностей этой модели.
