# Управление потоками данных

## Контракты

Каждый поток из data-flows.md имеет контракт:

- ID потока и версию;
- Producer и Consumer;
- бизнес-сущность и смысл передаваемых полей;
- обязательность, типы, допустимые значения;
- исходный ID и способ идентификации версии;
- время события, изменения и загрузки;
- правила создания, обновления и удаления;
- порядок обработки дублей и поздних изменений;
- контроль качества;
- владельцев, SLA и требования к доступу.

Схема хранится в репозитории и регистрируется в каталоге. Проверка сообщений выполняется на входе и в обработчике. Наличие каталога или реестра схем само по себе не валидирует данные.

## Доставка и идемпотентность

Для новых асинхронных потоков проектируется доставка at-least-once. Поэтому Consumer должен безопасно обрабатывать повторы.

- Ключ обработки: источник, тип сущности, локальный ID и версия либо ID события.
- Повтор одной версии не создаёт дополнительную запись.
- Позднее событие не перезаписывает более новое состояние без проверки версии.
- Для платежей защита от повторного исполнения остаётся в операционной системе. Дедупликация DWH её не заменяет.
- Подтверждение брокера означает приём сообщения, а не завершение бизнес-обработки.
- Порядок проверяется в пределах объекта; глобальный порядок между всеми источниками не предполагается.

Для batch используются ID пакета, контрольная сумма файла, ожидаемое количество записей и контрольная точка. Незавершённый пакет не публикуется как полный.

Число повторов, интервалы и срок хранения сообщений определяются по допустимому времени восстановления. После исчерпания попыток техническая ошибка передаётся в очередь ошибок.

## Начальная загрузка и текущие изменения

При сочетании снимка и CDC фиксируется согласованная граница: какие изменения уже вошли в снимок и с какой позиции продолжается журнал.

При отсутствии CDC используется подтверждённый механизм дельты с учётом удалений. Выборка только по updated_at без проверки его надёжности и правил границы недостаточна.

Контрольная точка продвигается после успешного сохранения данных. Повтор загрузки не должен давать пропуски или дубли.

## Качество и публикация

Проверки выполняются:

1. При приёме — формат, обязательные поля, версия.
2. В Hub — сопоставление, конфликты, источники доверия.
3. При подготовке DWH — ссылки, версии справочников, полнота.
4. Перед публикацией — финансовые сверки и бизнес-правила.

Финансовая сверка сравнивает одинаковый состав данных на одну дату и контрольную точку с учётом валют, статусов и правил расчёта.

При необъяснённом расхождении блокируется публикация затронутой витрины или пакета. Приём исходных данных и клиентские сервисы продолжают работать.

BI сохраняет доступ к последней проверенной версии с явным указанием даты актуальности.

## Карантин и технические ошибки

Техническая очередь содержит сообщения, не обработанные из-за временной недоступности, таймаута или другого технического сбоя.

DQ-карантин содержит записи, нарушающие правила качества или требующие бизнес-решения.

У каждой записи есть:

- ID потока, источника и объекта;
- причина и версия правила;
- время обнаружения;
- ответственный;
- статус и история действий;
- число попыток;
- результат повторной проверки.

Исправления не подменяют исходные данные без следа. Сохраняется связь с исходной записью и принятое решение.

## Эксплуатационный контроль

Мониторинг охватывает:

- успешность и длительность загрузок;
- задержку от источника до публикации;
- нагрузку источника;
- backlog, lag и возраст необработанных данных;
- ошибки контрактов;
- неразрешённые ссылки;
- финансовые расхождения;
- состояние карантина;
- актуальность каталога.

Для каждой метрики назначаются порог, получатель алерта и действие. До согласования этих параметров поток не считается готовым к промышленной эксплуатации.
