# DWH и Lakehouse

## Распределение данных

| Данные | DWH | Lakehouse | Причина |
| --- | --- | --- | --- |
| Клиенты | Исторические измерения с необходимыми атрибутами | Разрешённые атрибуты для конкретных сценариев | Единый ID нужен обоим контурам; полный профиль копируется только при обосновании |
| Счета и остатки | Согласованные измерения и снимки на дату | Подробная история при необходимости | Отчётности нужны проверенные состояния |
| Учётные движения | Проверенные факты Core | Исходная подробная история для повторной обработки | Разные назначения копий, одинаковые идентификаторы происхождения |
| Карточные события | Согласованные показатели и связи с движениями | Подробные события и их история | Авторизации и технические события не должны подменять проводки |
| Кредиты | Снимки портфеля и согласованные показатели | Подробная история состояний и изменений | Отделение официальных итогов от исследовательской детализации |
| Продукты, тарифы, справочники | Исторические измерения | Версии, необходимые для обработки | Оба контура используют согласованную семантику MDM |
| Обращения | Структурированные показатели | Текст только для разрешённого сценария | Минимизация чувствительных данных |
| Документы | Метаданные при необходимости | Извлечённые данные при необходимости | Сами файлы находятся в отдельной документной зоне объектного хранилища |

## Состояние на 3 месяца

Общий PostgreSQL содержит:

- staging — принятые исходные записи;
- согласованный слой — проверенные сущности и связи;
- витрины — наборы для BI;
- служебные таблицы загрузок, контрольных точек и результатов качества.

Это отдельная аналитическая БД. Рабочие БД банков не используются для запросов BI.

Существующие FU/RB DWH продолжают действующую регуляторную отчётность до сверки и переключения.

## Состояние на 12 месяцев

DWH сохраняет роль источника официальной отчётности.

Lakehouse строится на:

- объектном хранилище;
- Parquet для колоночных файлов;
- Apache Iceberg для управления аналитическими таблицами;
- совместимом каталоге таблиц;
- Trino для SQL-доступа и обработки.

DataHub является каталогом метаданных для пользователей и lineage. Он не заменяет технический каталог, необходимый движку для работы с таблицами Iceberg.

## Роли Iceberg и Trino

| Компонент | Роль | Что не делает |
| --- | --- | --- |
| Apache Iceberg | Управляет составом файлов таблицы, схемой и снимками состояния | Не является вычислительным движком или отдельным объектным хранилищем |
| Trino | Выполняет SQL-запросы и преобразования над доступными наборами | Не хранит исходные данные и не обеспечивает бизнес-качество автоматически |
| Объектное хранилище | Хранит файлы данных и метаданные таблиц | Само по себе не образует Lakehouse |
| DataHub | Показывает назначение, владельцев, схемы и происхождение | Не исполняет преобразования и не подменяет контроль доступа к данным |

Выбор конкретного каталога Iceberg и коннекторов подтверждается совместимостью и испытаниями.

## Слои Lakehouse

| Слой | Содержание | Правила |
| --- | --- | --- |
| Raw / Bronze | Принятые исходные наборы и события | Сохраняются источник, ID, версия, время и загрузка; доступ ограничен |
| Cleansed / Silver | Проверенные, нормализованные и сопоставленные данные | Устраняются дубли доставки, разрешаются ссылки, применяются общие коды |
| Published / Gold | Согласованные наборы для конкретных потребителей | Есть владелец, контракт, проверки и условия публикации |

Raw сохраняет исходный вид для трассировки и повторного расчёта. Это не означает бессрочное хранение или запрет согласованного удаления.

Каждый слой имеет назначение и политику хранения. Количество копий не увеличивается без потребности.

## Публикация показателей

Для каждого официального показателя фиксируются формула, источник фактов, период, статусы и правила корректировок.

Если набор рассчитывается в Lakehouse и публикуется в DWH, DWH не содержит независимую альтернативную формулу этого же показателя.

Исследовательские расчёты маркируются отдельно и не выдаются за официальные показатели.

## Ограничения

- PostgreSQL проверяется на реальных объёмах и профиле запросов.
- Lakehouse требует обслуживания файлов, снимков и метаданных.
- Большое количество мелких файлов увеличивает издержки обработки; предусматривается обслуживание таблиц.
- Доступ, удаление и сроки хранения согласуются для всех слоёв и резервных копий.
- Повторный расчёт должен фиксировать версии правил и справочников.
- Наличие двух контуров увеличивает эксплуатационную сложность; состав данных и ответственность должны быть явными.
