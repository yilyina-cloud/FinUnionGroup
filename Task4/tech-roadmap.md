# Технологическая дорожная карта

Статусы отражают решение проекта, а не подтверждённую зрелость технологий в компании:

- Adopt — используем в согласованной роли после приёмки.
- Trial — проверяем на пилоте до масштабирования.
- Assess — рассматриваем при подтверждении потребности.
- Hold — не расширяем применение.

## Технологический радар

| Зона | Технология / подход | Обоснование и условие |
| --- | --- | --- |
| Adopt | Customer Hub → MDM | Единая идентичность и справочники обязательны; внедрение поэтапное |
| Adopt | PostgreSQL DWH на 3 месяца | Подходит для первого согласованного объёма; ёмкость проверяется до запуска |
| Adopt | Airflow + dbt | Конечные batch-задачи, SQL-модели и проверки; не используются как потоковый движок |
| Adopt | DataHub | Каталог владельцев, контрактов и lineage критичных наборов |
| Adopt | Объектное хранилище | Документы, архивы и основа Lakehouse; доступ и восстановление проверяются |
| Trial | Kafka | Пилот доставки, повторов, восстановления и мониторинга до расширения потоков |
| Trial | Debezium / CDC | Зависит от исходных СУБД, прав, нагрузки и правил изменения схем |
| Trial | Iceberg + Trino | Целевой Lakehouse; проверяются каталог, коннекторы, история, обслуживание файлов и доступ |
| Trial | PostgreSQL для полного целевого DWH | Сохраняется при выполнении требований на ожидаемой нагрузке |
| Assess | Колоночная СУБД / MPP | Альтернатива, если целевой DWH не проходит испытания |
| Assess | Flink | Только при подтверждённой необходимости непрерывных расчётов с малой задержкой |
| Assess | Полный Data Mesh | Требует готовности доменных команд; пока используются data-продукты на общей платформе |
| Assess | Графовая БД / поисковый движок | Нужны отдельные обоснованные сценарии |
| Hold | Новые прямые интеграции с чужими БД | Увеличивают зависимость от внутренних схем |
| Hold | Новые независимые копии официальных показателей | Создают расхождения формул и ответственности |
| Hold | Расширение заменяемых legacy-контуров | Допускаются только необходимые изменения для непрерывности перехода |

Trial означает проверку внедрения, а не исключение компонента из целевой архитектуры Task3. При неуспешном пилоте пересматривается инструмент, но сохраняется необходимая функция.

## Последовательность

| Период | Возможности платформы | Поддерживаемый результат |
| --- | --- | --- |
| Месяцы 1–3 | Hub, PostgreSQL, batch-оркестрация, проверки и начальный каталог | Единые ID и общая управленческая отчётность |
| Месяцы 3–6 | Событийная доставка, пилоты CDC и Lakehouse, расширение lineage | Исторические и событийные наборы |
| Месяцы 6–10 | Масштабирование проверенных решений, MDM, доменные data-продукты | Перенос обслуживания и портфелей |
| Месяцы 9–12 | Проверенная отчётность, восстановление и эксплуатационная поддержка | Регуляторный cutover и отключение заменённых контуров |

Переход в эксплуатацию требует не только работающего инструмента, но и владельца, мониторинга, инструкции восстановления и подготовленной команды.
